# CDT 流量守护 · Cloudflare 部署指南

> 这份指南假设你**没写过代码**。每一步都写清楚了「做什么、为什么、看到什么算成功」。
> 遇到卡住的地方，把屏幕上整段内容发给我就行。

## 先搞清楚：这次装的是什么，为什么值得装

### 你原来那套的问题

原来的机器人装在**被监控的那台服务器自己身上**。这带来一个死结：

```
服务器流量超标 → 脚本把自己关机了（省钱 ✅）
              → 但脚本也一起死了
              → 下个月流量重置，没人去开机（复活 ❌）
```

我不是说它没用 —— **它省钱是真的**。但它救不了自己。你每个月都得手动去阿里云控制台点一次开机，忘了就一直停着。

### 这一套装的东西

把机器人搬到 **Cloudflare** 上跑。Cloudflare 是另一家公司的机房，跟你那台服务器没关系。

```
服务器流量超标 → 关机（省钱 ✅）
Cloudflare 上的机器人 → 它没跟着死，一直在跑
下个月流量重置 → 它发现机器还关着，自动开机（复活 ✅）
```

**这是唯一能真正解决死锁的办法。** 因为要叫醒一扇门里的人，你得站在门外。

### 花了多少钱

**免费。** Cloudflare 的免费额度远超我们的用量：

| 我们需要的 | 免费额度 | 实际用到的 |
|---|---|---|
| 定时任务 | 每天 10 万次请求 | 每天约 300 次 |
| 存储读写 | 每天 10 万次读 | 每天约 300 次 |
| 定时最小间隔 | 1 分钟 | 我们每 5 分钟一次 |

## 开始之前，先攒齐三样东西

按下表检查，缺哪样就先去办哪样。

### ① 一个 Cloudflare 账号

去 https://dash.cloudflare.com/sign-up 注册。邮箱 + 密码就行，不用绑卡。

### ② 一个 Telegram 机器人令牌

1. 在 Telegram 里搜索 **@BotFather**（注意是有官方认证标的那一个）
2. 发 `/newbot`
3. 它问名字，随便起，比如 `我的流量守护`
4. 它问用户名，**必须以 bot 结尾**，比如 `my_cdt_guard_bot`
5. 它会回一串令牌，长得像 `1234567890:AAHxxxxxxxxxxxxxxxxxxxxx`

**把这串令牌存好**，后面要用。

### ③ 你的 Telegram 数字 ID

1. 在 Telegram 里搜索 **@userinfobot**
2. 点「开始」
3. 它回你一条消息，里面 `Id:` 后面那串数字就是

这串数字的用途是：**只有你能操作机器人**，别人发消息它一个字都不回。

### ④ 阿里云的 AccessKey

去阿里云控制台 → 右上角头像 → 访问控制（RAM） → 用户 → 创建用户。

- 勾选「OpenAPI 调用访问」，它会给你 **AccessKey ID** 和 **AccessKey Secret**
- 权限至少要给：
  - `AliyunECSReadOnlyAccess`（查实例状态）
  - `AliyunECSSupportAccess` 或自定义含 `ecs:StartInstance` / `ecs:StopInstance` 的策略
  - `AliyunCDTReadOnlyAccess`（查流量）
  - `AliyunBSSReadOnlyAccess`（查余额账单）
- **Secret 只在创建时显示一次**，当场存好，关掉页面就再也看不到了

> 想省事的话，直接用主账号的 AK 也能跑。但**强烈建议用子账号**：万一泄露，损失可控。

## 部署（一条命令，它会带着你走完）

### 准备工作

装上 **Node.js**（如果没装过）：去 https://nodejs.org 下载 LTS 版，一路下一步。

装完打开终端（Windows 上叫 Git Bash 或 PowerShell），敲 `node -v`，能看到版本号就对了。

进入项目目录：

```bash
cd 你存放这个项目的位置/cdt-guard-worker
```

### 就这一条命令

```bash
bash deploy.sh
```

**对，就一条。** 它会依次带你走完 7 步，每一步都告诉你结果：

| 步骤 | 做什么 |
|---|---|
| 1 | 检查环境（Node、工具装好没有；缺了就当场自动装） |
| 2 | 打开浏览器让你登录 Cloudflare（点「允许」就行） |
| 3 | 创建存储空间，自动把 id 写进配置 |
| 4 | 问你要两项密钥（机器人令牌、网址密钥） |
| 5 | 把代码传上去 |
| 6 | **自动自检**（你不用动，它自己去连一次并把结果打在屏幕上） |
| 7 | **接着问你要监控哪几台机器**（见下方说明） |

**全程中文提示，跟着走就行。**

### 关于第 6 步的自动自检

以前自检是让你自己复制一串网址到浏览器打开。现在**不用了** ——
脚本会自己连一次，把结果直接打在终端里：

```
== 第 6 步 / 自动自检（你不用动，看着就行） ==
正在连接程序做自检，请稍等几秒...

=== CDT 流量守护 · 安装自检 ===
[成功] 命令菜单已注册
[成功] Webhook 已设置
--- 配置检查 ---
受监控机器数量: 0
```

看到 `[成功]` 就说明程序在线上跑着。看到 `[失败]` 它会告诉你怎么办。

### 关于第 7 步：为什么「填机器」也在这一条命令里

**你问得对，这本来就该在一条命令里。** 我原来把「装程序」和「填配置」
拆成两个脚本，理由是「先确认程序能跑再填数据」——但这理由站不住脚：
**用户根本分不清这两步的区别，只觉得「怎么还没弄完」。**

而且更实际的问题：一键脚本跑到这里，你刚登录完 Cloudflare、注意力在线，
这时候顺口问机器信息是最省事的。让你再单独跑第二条命令，
意味着要重新回到电脑前、重新进入状态。

所以现在第 7 步会直接问你（每项都有说明）：

- 你的 Telegram 数字 ID
- 每台机器的：名字、实例 ID、地域、AK、SK、流量阈值

填完会**把配置展示给你看一遍**（密钥自动打码），确认无误才写入。

> **现在不想填也行**：第 7 步开头直接回车就跳过，以后随时补：
> ```bash
> bash configure.sh
> ```

### 自动行为（不用你管）

| 什么时候 | 机器人做什么 |
|---|---|
| 每 5 分钟 | 查流量和状态；流量安全且机器停着 → 自动开机 |
| 流量超阈值 | 立刻强制关机止损，并通知你 |
| 流量用到 80% / 95% | 提前提醒你 |
| 余额低于警戒线 | 提醒你充值 |
| 机器被意外停机 | 立刻通知你（如果流量安全，会顺手开回来） |

### 「暂停监控」是什么意思

点「暂停监控」后，**脚本不再自动开关机**，但：

- 你手动点「开机」「关机」仍然有效
- 批量开关机**会跳过**它（尊重你不想让脚本碰它的意思）
- 流量超标也不会自动关机 —— 相当于「这机器我自己管」

再点一次「恢复监控」就回到自动模式。

## 常见问题

### 脚本跑到某一步，终端自己关了

**已修好**（如果你用的是旧版脚本会遇到）。一共修了四处，都是同一个类型的问题 ——
「不报错、不影响正常路径，只在特定条件下发作」：

| 症状 | 真正的原因 |
|---|---|
| 第 6 步打印指引时崩 | 抓网址用了管道接 `head`，Git Bash 下会让脚本被强制终止 |
| 「还没安装部署工具」误报 | 用了 `npx --no-install`，项目里没装工具时每个调用都失败 |
| 刷出一屏英文帮助 | wrangler 3.x 不认 `--remote` 参数 |
| 配置脚本被引用时整个流程崩 | 顶层有个裸 `exit`，把调用它的 `deploy.sh` 一起杀了 |

**关键认知**：终端关了**不等于部署失败**。程序可能已经传上去了。
用下面这条命令查真实状态：

```bash
node_modules/.bin/wrangler deployments list
```

只要能看到时间最新的那条记录，就说明代码在线上跑着。

### 机器人不理我

1. 确认发消息用的是**配置里那个数字 ID** 对应的账号（别人发它不理，这是设计）
2. 打开自检网址看 Webhook 状态那一栏
3. 如果显示「待处理消息数」一直在涨，说明 Webhook 没通

### 提示「查询失败」

一般是这几种原因：

- **AK 权限不够** —— 去阿里云检查那个子账号有没有放开机和查询权限
- **地域填错了** —— 实例在 `cn-hangzhou` 你填了 `ap-southeast-1`，查不到
- **实例 ID 写错** —— 少一位或大小写不对

机器人会**明确告诉你失败原因**，不会假装查到了 0。

### 忘记了访问网址

```bash
cat .worker-url
```

部署时会把网址记在这个文件里。如果没有这个文件（旧版没有这个功能）：

```bash
# 看部署记录确认它在跑
node_modules/.bin/wrangler deployments list

# 网址一般是：https://cdt-guard.你的Cloudflare账号名.workers.dev
# 账号名就是浏览器打开 dash.cloudflare.com 后地址栏里那串
```

### 忘记了网址密钥

新版部署会把它记在本地一个小文件里，直接看就行：

```bash
cat .webhook-secret
```

> 这个文件里存的是**你自己编的**网址密钥，不是云厂商发的凭据，所以存下来是安全的
> （机器人令牌那种高敏感的东西绝不存盘）。

**旧版装的、或者本地文件也没了**，重设一个即可
（不影响已部署的代码，但要顺便重新绑定 Telegram）：

```bash
# 1. 重设密钥（把 新密钥 换成你自己编的一串）
printf '%s' '我的新密钥' | node_modules/.bin/wrangler secret put WEBHOOK_SECRET

# 2. 等约 10 秒让它生效，然后打开自检页重新绑定
#    https://你的网址/setup?key=我的新密钥
```

自检页会自动把新的收信地址告诉 Telegram，不用手动改。

> 最省事的办法其实是**重跑一次部署**：`bash deploy.sh`
> 它会重新问密钥、重新部署、重新自检，全程帮你串起来。

### 提示 `--remote` 不是有效参数 / 刷出一屏英文

**已修好。** 原因是 wrangler 3.x 和 4.x 的命令参数不一样（4.x 才有 `--remote`）。
现在脚本做了版本兼容，两种都能跑。

如果看到一屏英文，直接**翻到最下面几行**看结果就行 —— wrangler 的报错
前面很长一段都是「要不要上报给 Cloudflare」之类的废话。

### 为什么要看「账号汇总」而不是逐台看


**因为免费额度是按账号算的，不是按机器算的。**

同一个账号下 3 台机器，共享一份 200GB，不是每台 200GB。

> 三台各用 70GB，逐台看每台都很安全 —— 加起来 210GB 其实已经超了。

「账号汇总」会把同一个 AccessKey 的机器合并算，告诉你这个账号总共用了多少。

### 周报显示「数据点不足」

正常。周报依赖每天攒的流量快照，**至少要跑满 2 天**才有趋势线。

刚装完就看，它不会拿 0 糊弄你，只会老实说「还没攒够」。

### 流量超标关机后，下个月真的会自动开机吗

**会 —— 这正是装到 Cloudflare 上的意义。**

Cloudflare 上的机器人不跟着关机，它一直在跑。下个月账期重置、流量归零，下一次巡检（最多 5 分钟后）就会发现「流量安全了 + 机器还关着」，然后自动开机。

## 出了问题怎么回滚

### 想临时停掉自动开关机

在 Telegram 里对要停的机器点「暂停监控」。或者直接删掉定时任务：

```bash
npx wrangler triggers deploy --cron ""
```

### 想彻底删掉

```bash
npx wrangler delete
```

代码和定时任务都没了。**KV 里的数据还在**（配置、台账），想回来重新部署即可。

### 想回到原来那套（装在服务器上的版本）

原来那套仍在你的服务器上，本方案没有动它。停掉它的服务即可：

```bash
# 在服务器上执行
systemctl stop cdt-guard-bot
systemctl disable cdt-guard-bot
```

两套不要同时开 —— 会重复发通知、重复开关机。

### 为什么不能用阿里云官方 SDK

Cloudflare Workers 跑在 V8 隔离环境里，不能装 node 的 SDK（依赖了 Node 的文件系统和原生模块）。

所以这里**手写了 RPC 签名**（HMAC-SHA1），用 Web Crypto API 实现。

### 一个坑：`SignatureType` 必须参与签名

阿里云的 RPC 签名里有个 `SignatureType` 参数，值为空字符串。

**这个看起来毫无意义的空参数必须参与签名计算** —— 少了它，签名不匹配，报 `SignatureDoesNotMatch`。

官方文档没强调这一点，实测对比过：
- 不含 → `1G1FVxj2al4acFg8+dsAK2wWuOM=` ❌
- 含（空值）→ `3sWYY1r9PaR1k3X/oi5n5hOEXNQ=` ✅

### 为什么收消息改成 Webhook

Workers 不能跑常驻进程，长轮询（`while True: getUpdates`）不可行。

改成 Webhook 后：你点按钮 → Telegram 主动 POST 到 Cloudflare → 处理完就结束。

这不是妥协 —— 这恰恰是无服务器环境的正确用法，而且**天然解决了「进程会死」的问题**。

### 存储为什么用 KV 而不是文件

Workers 没有磁盘。所有原本存文件的东西都搬进了 KV：

| 键名 | 存什么 |
|---|---|
| `config` | 机器清单、阈值、Chat ID |
| `state` | 上次告警时间、连续失败次数 |
| `traffic_history` | 流量台账（周报数据源） |
| `sessions` | 三级菜单「刚点的是哪台机器」 |

### 流量台账为什么按天去重

巡检每 5 分钟一次，一天 288 条 × 台数，全留会撑爆存储。

而周报看的是**每日趋势**，5 分钟精度没意义。所以同一台机器同一天只保留最新一条。

### 本地自检怎么跑

```bash
bash tests/run-all.sh
```

会跑 129 项检查（菜单文案 27 项 + 集成 73 项 + 部署脚本 29 项），覆盖：

- emoji 转义是否正确（Python 的 `\U0001f4ca` 在 JS 里会变成字面文本！）
- 密钥遮蔽是否会死循环（踩过这个坑）
- Markdown 安全预判
- 台账去重语义
- 空配置不崩
- **部署脚本的被引用安全性**（顶层 `exit` 会不会误杀调用方）
- **临时文件是否延迟创建**（只读操作不该留垃圾）
- **密钥变量是否真的被赋值**（自动自检依赖它）

**不需要联网，不需要密钥。**

## 改了什么（本轮）

这一轮主要是**把「填机器」合并进了一键脚本**，外加修掉几处
「引用另一个脚本时会连带崩」的隐患：

| 改动 | 为什么 |
|---|---|
| 部署完直接接着问机器信息 | 用户分不清「装程序」和「填配置」，只觉得「怎么还没弄完」 |
| 配置逻辑统一收在 `run_configure()` | 原来两边各有一份，早晚会走偏（改一处忘一处） |
| 新增自动自检步骤 | 用户不用自己抄网址去浏览器打开 |
| 网址密钥存一份到本地 | 自动自检要用；它是自己编的，不是云厂商凭据 |
| 配置脚本的顶层 `exit` 收进函数 | 否则会把引用它的部署脚本一起杀掉 |
| 临时文件改为延迟创建 | 只读操作（`show`）不该留下垃圾文件 |
